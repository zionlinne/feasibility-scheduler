# Feasibility Scheduler

Clean-room Feasibility Scheduler (kernel + adapters). Local package pushed from the author's machine for cloud iteration.

Constraints for experiments: do not modify the scheduler kernel core for adapter-only work; keep adapter changes at the adapter/entry layer.

## Contract planning

The real legacy adapter creates a version 2 contract before dispatch. A supplied
`TASK_INPUT.contract_plan` enables reproducible offline runs. The source ledger is
generated by `adapters.contract_checks.requirement_ledger(TASK_text)`. The model
returns requirement IDs; the host attaches original text and hashes. Supplied
offline plans must contain the original ledger. Each nonempty source line has a stable ID
and source hash. Every requirement must be referenced by at least one check.
This is a coverage check; a reviewer must still assess whether the checks capture
the meaning of the source requirement.

Checks have `id`, `requirements` (source IDs), and `kind`. Supported kinds are
`file_exists` (`path`), `text_contains` (`path`, nonempty `value`), `json_equals`
(`path`, `key`, `value`), `json_match` (`path`, `key`, `other_path`, `other_key`),
and `manual` (`note`). JSON keys are lists of object keys. Paths must belong to
declared artifacts. A manual obligation remains UNVERIFIED and blocks success.
Text-only version 1 plans require migration before runtime enforcement.

Optional `decompositions` contain `parent` and `children`, each with `id`,
`owned_files`, and `postcondition`. Children partition the parent's artifacts
exactly, including data and document artifacts. The scheduler selects among these
and its existing candidates. Each selected split/merge gets a fresh execution
contract; checks spanning children are deferred to mandatory root composition.
The root task rechecks all checks against the final workspace.

Failed checks generate persisted counterexamples and bounded repair requests.
`--contract-repair-limit` defaults to 1 per work unit; 0 disables repair. Repair
keeps the original checks and source requirements. Unknown/manual checks and
repair transport failures require recovery. Audit files are `contract.json`,
`contract-checks-*.json`, `contract-repair-*.json`, and `summary.json`.

Targeted offline validation uses
`py -m pytest tests/test_contract_plan.py tests/test_contract_runtime.py -q`.
The executable checker vocabulary is deliberately limited. It does not establish
general semantic correctness of natural-language contracts or support concurrent
writers to the same artifact.

## Native agent execution

`--client native --native-bridge-dir <directory>` uses filesystem rendezvous.
The host must dispatch its native agents for each `.request.json` and atomically
publish the matching `.response.json` containing `status`, `producer`, and `body`.
The scheduler retains dispatch, dependency, split/merge, acceptance, and trace
ownership. This transport opens no network connection and does not launch models
itself. Pending requests are UNKNOWN after a timeout; response lookup survives a
client restart. Native token usage is left unknown rather than fabricated.

Trusted integration checks can be registered through
`LegacyDocConfig.external_checkers`, with names explicitly allowed in task input
`external_checker_names`. Contract checks use `kind: external`, `name`, and owned
`paths` defining the repair scope. Model output cannot supply shell commands.
An unconfigured or broken checker remains UNVERIFIED. The host decides the actual
verification program and maps its real result to passed/failed/unverified.

## Single-root planning and supplied acceptance

For the legacy material layout, `package.json` and `public/` beside TASK.md are
automatically registered as read-only references. Private verifier files and
generated source files are excluded. An explicitly supplied reference cannot
silently conflict with the on-disk material. The resolved input is recorded in
`effective-task-input.json`.

`modules` is a contract catalog. It contains every initial task plus optional
child contracts explicitly named in `decompositions`. Children remain inactive
until FBS selects the split. Their declared execution dependencies and handoffs
then enter the new execution contracts. Ownership must partition the parent
exactly; unknown children, overlapping ownership, cycles and invalid references
remain errors. `shared_interfaces` may be an interface-specification reference,
and never creates an execution wait.

Use `--acceptance-script /absolute/private/verify-v3.mjs` to register the trusted
Node verifier as `task-acceptance`. The script is called with the absolute
solution directory and a fresh JSON report path. New plans can reference this
checker using `kind: external`. Existing manual obligations remain UNVERIFIED;
passing preflight or syntax checks does not imply business acceptance.

Planner validation writes `contract-candidate.json` and
`contract-validation.json`, including failed candidates. It does not silently
retry paid model calls or discard constraints to force a plan through validation.

## Acceptance profiles and planner responsibilities

The HTTP/native CLI now loads the host-owned `software-v1` profile by default.
It fixes seven acceptance obligations (requirements, artifacts, build/startup,
components/interfaces, integration, functionality, regression), without fixing
module boundaries, agent count, or DAG. For behavior categories it requires an
external checker approved by the host. `--acceptance node-check` remains a syntax
check and cannot discharge these obligations. Supply `--acceptance-script` for
the default `task-acceptance` checker. Missing mandatory capability is rejected
before creating a model client, so there is no paid generation just to discover
that the run cannot be verified.

```powershell
py scripts/run_legacy_doc_task.py --client http --task-input TASK_INPUT.json --task-md TASK.md --acceptance node-check --acceptance-script C:/materials/private/verify-v3.mjs --max-concurrency 8
```

Custom profiles can be supplied in host task input `acceptance_profile`, through
`LegacyDocConfig.acceptance_profile`, or `--acceptance-profile profile.json`.
Conflicting host configurations are rejected. Library callers and fake CLI runs
without a profile retain legacy behavior; they do not acquire the new preflight
guarantee. The profile is attached by the host, hashed with the immutable plan,
and cannot be weakened by the planner. Categories use `id`, `description`,
`applicable`, `allowed_kinds`, and `checker_names` (for external evidence). Only
the host may set `applicable: false`, with a nonempty `reason`; a planner cannot
invent N/A decisions. A twelve-category transactional resource management example
is in `docs/acceptance-profiles/transactional-resource-v1.json`.

The planner returns responsibility mappings, for example:

```json
{
  "acceptance_assignments": [
    {
      "id": "root-behavior",
      "category": "functional",
      "requirements": ["R1"],
      "owners": ["__contract_composition__"],
      "checks": ["integration-suite"],
      "scope": "root"
    }
  ]
}
```

Each check still defines its real predicate, source IDs, and artifacts. Assignments
must cover every applicable category, source requirement, and check. `local`
has one logical task owner; `cross` has multiple owners and is checked at root;
`root` is owned by `__contract_composition__`. Proposed child IDs are legal owners.
External checkers inspect the composed workspace and always run at root, even if
their repair scope is a single file. Checks shared across assignments use the
most restrictive scope. No manual check is executable in profile-enabled runs.
Undeclared owners, missing coverage, unregistered/noncallable external checkers,
and predicate kinds too weak for the selected category block implementation
dispatch. Failed capability checks persist in `acceptance-preflight.json`; failed
generated plans also retain candidate and validation diagnostics.

Split/merge rewrites preserve the full profile and assignments. Execution contracts
project relevant responsibilities by artifact/check scope and logical task IDs;
a check spanning new children is deferred to composition, never dropped. Final
composition rechecks all obligations and feeds concrete failures to bounded repair.
Local ACCEPTED still describes that work unit's configured checks, not whole-task
business acceptance.

A checker name is not a proof of semantic coverage. The host must select a suite
that actually tests each category it is approved for; one independent suite may
be reused across categories only to the extent of its coverage. Category/ID
validation cannot infer natural-language meaning or prove arbitrary programs.
The profile does not generate missing business tests or convert unknown results
into passes. No automatic paid planning retries are added.
