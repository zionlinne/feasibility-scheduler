# Feasibility Scheduler

Clean-room Feasibility Scheduler (kernel + adapters). Local package pushed from the author's machine for cloud iteration.

Constraints for experiments: do not modify the scheduler kernel core for adapter-only work; keep adapter changes at the adapter/entry layer.

## Contract planning

The real legacy adapter creates a version 2 contract before dispatch. A supplied
`TASK_INPUT.contract_plan` enables reproducible offline runs. The source ledger is
generated by `adapters.contract_checks.requirement_ledger(TASK_text)`. The model
returns requirement IDs; the host attaches original text and hashes. Supplied
offline plans must contain the original ledger. Each nonempty source line has a stable ID
and source hash. Every requirement must be referenced by at least one check.
This is a coverage check; a reviewer must still assess whether the checks capture
the meaning of the source requirement.

Checks have `id`, `requirements` (source IDs), and `kind`. Supported kinds are
`file_exists` (`path`), `text_contains` (`path`, nonempty `value`), `json_equals`
(`path`, `key`, `value`), `json_match` (`path`, `key`, `other_path`, `other_key`),
and `manual` (`note`). JSON keys are lists of object keys. Paths must belong to
declared artifacts. A manual obligation remains UNVERIFIED and blocks success.
Text-only version 1 plans require migration before runtime enforcement.

Optional `decompositions` contain `parent` and `children`, each with `id`,
`owned_files`, and `postcondition`. Children partition the parent's artifacts
exactly, including data and document artifacts. The scheduler selects among these
and its existing candidates. Each selected split/merge gets a fresh execution
contract; checks spanning children are deferred to mandatory root composition.
The root task rechecks all checks against the final workspace.

Failed checks generate persisted counterexamples and bounded repair requests.
`--contract-repair-limit` defaults to 1 per work unit; 0 disables repair. Repair
keeps the original checks and source requirements. Unknown/manual checks and
repair transport failures require recovery. Audit files are `contract.json`,
`contract-checks-*.json`, `contract-repair-*.json`, and `summary.json`.

Targeted offline validation uses
`py -m pytest tests/test_contract_plan.py tests/test_contract_runtime.py -q`.
The executable checker vocabulary is deliberately limited. It does not establish
general semantic correctness of natural-language contracts or support concurrent
writers to the same artifact.

## Native agent execution

`--client native --native-bridge-dir <directory>` uses filesystem rendezvous.
The host must dispatch its native agents for each `.request.json` and atomically
publish the matching `.response.json` containing `status`, `producer`, and `body`.
The scheduler retains dispatch, dependency, split/merge, acceptance, and trace
ownership. This transport opens no network connection and does not launch models
itself. Pending requests are UNKNOWN after a timeout; response lookup survives a
client restart. Native token usage is left unknown rather than fabricated.

Trusted integration checks can be registered through
`LegacyDocConfig.external_checkers`, with names explicitly allowed in task input
`external_checker_names`. Contract checks use `kind: external`, `name`,
`read_paths` (owned outputs or registered read-only materials), and `repair_paths`
(only owned outputs; an empty list forbids repair). Model output cannot supply shell commands.
An unconfigured or broken checker remains UNVERIFIED. The host decides the actual
verification program and maps its real result to passed/failed/unverified.

## Single-root planning and supplied acceptance

For the legacy material layout, `package.json` and `public/` beside TASK.md are
automatically registered as read-only references. Private verifier files and
generated source files are excluded. An explicitly supplied reference cannot
silently conflict with the on-disk material. The resolved input is recorded in
`effective-task-input.json`.

`modules` is a contract catalog. It contains every initial task plus optional
child contracts explicitly named in `decompositions`. Children remain inactive
until FBS selects the split. Their declared execution dependencies and handoffs
then enter the new execution contracts. Ownership must partition the parent
exactly; unknown children, overlapping ownership, cycles and invalid references
remain errors. `shared_interfaces` may be an interface-specification reference,
and never creates an execution wait.

Use `--acceptance-script /absolute/private/verify-v3.mjs` to register the trusted
Node verifier as `task-acceptance`. The script is called with the absolute
solution directory and a fresh JSON report path. New plans can reference this
checker using `kind: external`. Existing manual obligations remain UNVERIFIED;
passing preflight or syntax checks does not imply business acceptance.

Planner validation writes `contract-candidate.json` and
`contract-validation.json`, including failed candidates. It does not silently
retry paid model calls or discard constraints to force a plan through validation.

## Acceptance profiles and planner responsibilities

The HTTP/native CLI now loads the host-owned `software-v1` profile by default.
It fixes seven acceptance obligations (requirements, artifacts, build/startup,
components/interfaces, integration, functionality, regression), without fixing
module boundaries, agent count, or DAG. For behavior categories it requires an
external checker approved by the host. `--acceptance node-check` remains a syntax
check and cannot discharge these obligations. Supply `--acceptance-script` for
the default `task-acceptance` checker. Missing mandatory capability is rejected
before creating a model client, so there is no paid generation just to discover
that the run cannot be verified.

```powershell
py scripts/run_legacy_doc_task.py --client http --task-input TASK_INPUT.json --task-md TASK.md --acceptance node-check --acceptance-script C:/materials/private/verify-v3.mjs --max-concurrency 8
```

Custom profiles can be supplied in host task input `acceptance_profile`, through
`LegacyDocConfig.acceptance_profile`, or `--acceptance-profile profile.json`.
Conflicting host configurations are rejected. Library callers and fake CLI runs
without a profile retain legacy behavior; they do not acquire the new preflight
guarantee. The profile is attached by the host, hashed with the immutable plan,
and cannot be weakened by the planner. Categories use `id`, `description`,
`applicable`, `allowed_kinds`, and `checker_names` (for external evidence). Only
the host may set `applicable: false`, with a nonempty `reason`; a planner cannot
invent N/A decisions. A twelve-category transactional resource management example
is in `docs/acceptance-profiles/transactional-resource-v1.json`.

The planner returns responsibility mappings, for example:

```json
{
  "acceptance_assignments": [
    {
      "id": "root-behavior",
      "category": "functional",
      "requirements": ["R1"],
      "owners": ["__contract_composition__"],
      "checks": ["integration-suite"],
      "scope": "root"
    }
  ]
}
```

Each check still defines its real predicate, source IDs, and artifacts. Assignments
must cover every applicable category, source requirement, and check. `local`
has one logical task owner; `cross` has multiple owners and is checked at root;
`root` is owned by `__contract_composition__`. Proposed child IDs are legal owners.
External checkers inspect the composed workspace and always run at root, even if
their repair scope is a single file. Checks shared across assignments use the
most restrictive scope. No manual check is executable in profile-enabled runs.
Undeclared owners, missing coverage, unregistered/noncallable external checkers,
and predicate kinds too weak for the selected category block implementation
dispatch. Failed capability checks persist in `acceptance-preflight.json`; failed
generated plans also retain candidate and validation diagnostics.

Split/merge rewrites preserve the full profile and assignments. Execution contracts
project relevant responsibilities by artifact/check scope and logical task IDs;
a check spanning new children is deferred to composition, never dropped. Final
composition rechecks all obligations and feeds concrete failures to bounded repair.
Local ACCEPTED still describes that work unit's configured checks, not whole-task
business acceptance.

A checker name is not a proof of semantic coverage. The host must select a suite
that actually tests each category it is approved for; one independent suite may
be reused across categories only to the extent of its coverage. Category/ID
validation cannot infer natural-language meaning or prove arbitrary programs.
The profile does not generate missing business tests or convert unknown results
into passes. No automatic paid planning retries are added.

Before strict responsibility validation, the host can complete missing **root**
evidence references using checks already in the plan. Candidates must explicitly
declare the missing source IDs and satisfy that category's predicate/checker
policy. All missing IDs must have approved evidence before any link is added.
Only the assignment's check-ID list changes; source requirements, test predicates,
owners and scopes remain untouched. No new checks or coverage claims are invented,
and local responsibilities are not reassigned. Missing or weaker evidence still
blocks dispatch. This is evidence-index compilation, not a semantic proof or an
extra model call. Raw candidates remain unchanged; added links and source IDs are
recorded in `contract-validation.json` for generated plans or
`acceptance-preflight.json` for supplied plans. Strict errors name the missing IDs
and attached checks. The compiled `contract.json` is frozen before execution.

### External reads versus repair permission

```json
{
  "id": "public-flow",
  "kind": "external",
  "name": "task-acceptance",
  "read_paths": ["cli.mjs", "public/flow.input.json", "public/flow.expected.json"],
  "repair_paths": ["cli.mjs"],
  "requirements": ["R1"]
}
```

Provided metadata and samples may be read by acceptance but never assigned as
model repair targets. Repair feedback contains only the assigned output files;
both local and composition redelivery reject additional files before writing.
Local subset repairs still validate the repaired files and recheck all local
obligations against unchanged files. Composition still rechecks the full plan.

Legacy external `paths` remains supported as the read/relevance list; repair
permission is inferred as its intersection with the host-owned output set. Thus
old plans containing registered sample paths work without editing or dropping
checks, while reference-only checks cannot trigger model repairs. Do not mix
legacy `paths` with new scope fields. New scope fields must both be present;
unknown reads, unowned repairs and malformed lists are rejected with the check
ID, field name and invalid paths. These fields control contract responsibility
and model repair authorization, not operating-system isolation of a trusted
host checker, which still receives the workspace directory.

### Composition repair and verification versions

Composition validates the existence of **all** owned outputs and reruns the
configured foundation checks, including `node --check` in node-check mode,
before running business predicates. This happens on the initial root evaluation
and after every repair. Invalid repaired syntax cannot inherit an earlier child
pass; validator failures remain UNVERIFIED. Failed syntax identifies its output
file as the repair target. Interface behavior still requires real integration
tests; a syntax check alone does not establish interface compatibility.

Repair feedback separates editable `artifacts` from `read_only_artifacts`. The
latter contains current file contents from relevant check read scopes and is
included in the model prompt, so a consumer repair can inspect its provider.
These context files never expand repair authorization; redelivery still requires
exactly the authorized output subset. Missing context files are shown as null.

Within one evaluation, aliases of the same named workspace checker reuse one
result per observed artifact version. Version hashes cover declared check paths,
all host-owned outputs, and registered root reference paths. Every alias retains
its own source/category links, result and executed/reused audit marker. Passed,
failed and UNVERIFIED results are all shared without turning unknowns into passes.
A new repair/evaluation round starts fresh; changes invalidate the version, and
a checker that changes observed artifacts cannot produce a valid pass. This is
per-evaluation memoization, not a persistent cache or a new retry policy.

### Exhausted merged requests and actual module participation

In rewrite mode, a merged multi-file task that exhausts its existing server-error
retries can be split back into per-file tasks once. The failed task stays in the
audit history, active dependencies are retargeted, and the recovered children
cannot merge again or trigger another fallback split. Already accepted peers are
preserved. TIMEOUT/UNKNOWN are not treated as confirmed failures and never trigger
this fallback. The ordinary per-task retry limit still applies to the new tasks;
this is a bounded change of delivery shape, not a guarantee that an unavailable
provider will recover. Fixed-DAG mode retains its existing behavior.

When `--acceptance-script` is used, all selected owned `.js/.mjs/.cjs` outputs
must have execution evidence from that actual Node suite. The host enables V8
coverage in the verifier and inherited Node subprocesses, records actual process
entrypoints, and flushes server coverage before HTTP response completion so a
subsequent forced server stop cannot erase it. The trusted preload lives outside
the solution; source files are not rewritten. Worker prompts explicitly require
shared-interface collaboration rather than duplicating sibling responsibilities.

Root acceptance fails even with a passing business report if required modules
were never loaded, or a loaded non-entrypoint module contains functions but none
were called. Actual entrypoint execution and constant-only modules are handled
separately. `module-execution-N.json` records required files, loaded/called flags
and missing evidence; raw V8 evidence remains in `module-coverage-N/`. Integration
repair context includes current peer output contents without granting write access.

These observations block unused-module/monolithic bypasses like a runtime that
ignores all generated domain files. They are necessary execution witnesses, not
proof that every module fulfills its entire semantic responsibility or every
branch was tested. The business suite remains mandatory. This automatic witness
is Node-specific; other runtimes require their own trusted acceptance adapters.
Host-owned test/helper files that the selected suite never executes will also be
reported as missing evidence; choose the ownership/verification scope accordingly.

### Explicit integration stage before root acceptance

Set host `integration_files` in TASK_INPUT (an array), or pass
`--integration-files src/runtime.mjs,src/cli.mjs` to authorize a sequential
`__contract_integration__` task. Paths must be unique canonical paths already
owned by the selected producers; references cannot be edited. This opt-in stage
requires a real/native client and an executable v2 contract. It does not change
the default workflow or automatically grant the planner broader write access.

The integration task waits for all producers to be ACCEPTED, including replacement
children introduced by graph rewrites. At dispatch it reads the actual delivered
outputs and reference materials, with hashes recorded in `integration-context.json`.
The configured worker receives current editable sources, read-only peer sources,
and the immutable contract. Its job is to connect existing interfaces through the
authorized files, preserving peer implementations rather than duplicating them.
Only the complete contents of the authorized files may be returned. Integration
has no duplicate ownership and cannot itself be split or merged by the scheduler.

The stage makes one worker request: no transport retry, format-repair request or
contract-repair request. TIMEOUT requires recovery; other unsuccessful responses
fail the stage. An unavailable source prevents the request. Delivery or configured
syntax acceptance alone does not prove integration correctness: the root waits
for this stage and independently rechecks all original predicates and trusted
business/execution checks. Root failure is reported without another model repair
when this stage is enabled. A failed candidate may remain in the authorized
workspace for inspection; accepted producer history describes the earlier version,
and the integration delivery hashes identify the replacement version.

This provides an automatic place for integration work, not a guarantee that a
model will produce a correct integration. Keep the edit scope small enough for
the worker's output budget; existing peer implementations stay read-only. The
lightweight regression uses scripted workers and one real Node entrypoint check;
it does not demonstrate paid-provider reliability or re-run the original full task.
