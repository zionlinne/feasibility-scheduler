# Feasibility Scheduler

Clean-room Feasibility Scheduler (kernel + adapters). Local package pushed from the author's machine for cloud iteration.

Constraints for experiments: do not modify the scheduler kernel core for adapter-only work; keep adapter changes at the adapter/entry layer.

## Contract planning

The real legacy adapter creates a version 2 contract before dispatch. A supplied
`TASK_INPUT.contract_plan` enables reproducible offline runs. The source ledger is
generated by `adapters.contract_checks.requirement_ledger(TASK_text)` and must be
copied unchanged into `requirements`. Each nonempty source line has a stable ID
and source hash. Every requirement must be referenced by at least one check.
This is a coverage check; a reviewer must still assess whether the checks capture
the meaning of the source requirement.

Checks have `id`, `requirements` (source IDs), and `kind`. Supported kinds are
`file_exists` (`path`), `text_contains` (`path`, nonempty `value`), `json_equals`
(`path`, `key`, `value`), `json_match` (`path`, `key`, `other_path`, `other_key`),
and `manual` (`note`). JSON keys are lists of object keys. Paths must belong to
declared artifacts. A manual obligation remains UNVERIFIED and blocks success.
Text-only version 1 plans require migration before runtime enforcement.

Optional `decompositions` contain `parent` and `children`, each with `id`,
`owned_files`, and `postcondition`. Children partition the parent's artifacts
exactly, including data and document artifacts. The scheduler selects among these
and its existing candidates. Each selected split/merge gets a fresh execution
contract; checks spanning children are deferred to mandatory root composition.
The root task rechecks all checks against the final workspace.

Failed checks generate persisted counterexamples and bounded repair requests.
`--contract-repair-limit` defaults to 1 per work unit; 0 disables repair. Repair
keeps the original checks and source requirements. Unknown/manual checks and
repair transport failures require recovery. Audit files are `contract.json`,
`contract-checks-*.json`, `contract-repair-*.json`, and `summary.json`.

Targeted offline validation uses
`py -m pytest tests/test_contract_plan.py tests/test_contract_runtime.py -q`.
The executable checker vocabulary is deliberately limited. It does not establish
general semantic correctness of natural-language contracts or support concurrent
writers to the same artifact.

## Native agent execution

`--client native --native-bridge-dir <directory>` uses filesystem rendezvous.
The host must dispatch its native agents for each `.request.json` and atomically
publish the matching `.response.json` containing `status`, `producer`, and `body`.
The scheduler retains dispatch, dependency, split/merge, acceptance, and trace
ownership. This transport opens no network connection and does not launch models
itself. Pending requests are UNKNOWN after a timeout; response lookup survives a
client restart. Native token usage is left unknown rather than fabricated.

Trusted integration checks can be registered through
`LegacyDocConfig.external_checkers`, with names explicitly allowed in task input
`external_checker_names`. Contract checks use `kind: external`, `name`, and owned
`paths` defining the repair scope. Model output cannot supply shell commands.
An unconfigured or broken checker remains UNVERIFIED. The host decides the actual
verification program and maps its real result to passed/failed/unverified.
